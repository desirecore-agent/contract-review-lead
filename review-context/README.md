# Lead review context

`review-context.yaml` is a closed, Lead-owned declaration record for a single frozen O0 case. It separates an explicitly requested review perspective and a candidate jurisdiction review basis from file identity, Delegate identity, Human Gate approval, and legal conclusions.

Before its first write, Lead reads both this record's schema and template, writes from that template, and reads the result back against the closed branches. A readable YAML file is not evidence of schema conformity. When the user limits the turn to registration or context completion, `review-registration` is the sole procedure: that expressed scope is final for the turn, so Lead creates only this closed record and does not infer material facts, preflight packs, freeze an inventory, build a matrix, delegate, or begin review. Later clarification alone does not expand that user-granted scope. On a same-case, same-material update, Lead reads the existing record and writes `revision + 1` only if the closed record actually changes.

The record may cite only an explicit current-request user statement, one identified current-contract part with its O0 SHA-256 and a bounded locator, or a verified Intake S8 receipt reference. These are source claims that Lead must check against the case artifacts; none certifies party representation, authority, legal applicability, or platform identity. In particular, `review_subject_label` asks whose commercial perspective should guide directional analysis. It does not say that the user represents that contractual party.

`jurisdiction.status: candidate_basis` retains exactly one stated or current-part-clue candidate; the basis remains a review basis, not a final governing-law or forum conclusion. A limited O0 that has not authorized a pack preflight uses only `pack: {status: not_prechecked}`, `not_issued_pack_preflight_pending`, and `PEND-JURISDICTION-PACK-PREFLIGHT` from Lead. That records an authorization boundary, not a pin, a failure, or permission to run a tool. After the user authorizes complete review, Lead must perform the actual preflight: a successful read, supported scope, and pins become `read_and_pinned`; an actual failure becomes `unavailable`, `RULE_SOURCE_UNAVAILABLE`, and the existing stop rule. `undetermined` requests clarification and permits factual extraction only. `conflicting` retains all candidates, chooses none by default, and routes `HG-02`; an unprechecked candidate cannot remove or resolve that gate.

`output_constraints` limits what a downstream analysis may issue. It never proves an output was issued, grants file or tool access, satisfies a Human Gate, or authorizes Delegate continuation. Missing stance suppresses only directional risk, redline, and negotiation advice. Missing, conflicting, or not-prechecked jurisdiction suppresses only jurisdiction-specific substantive conclusions. None suppresses factual extraction or an otherwise user-authorized full-review intake step.

When a user supplies a clarification without replacing submitted material, Lead writes a higher `revision` bound to the same case and current-manifest state, preserves the old record in the ledger history, and re-runs only affected analysis through ordinary `isolated` orchestration. It must not invent a work-context ID, reuse an old summary as identity, or call this platform `continue` or action resume. O3 and reporter handoffs use exactly `review_context_path`, `review_context_case_id`, `review_context_revision`, `review_context_current_manifest`, and `review_context_output_constraints`. Each member receipt returns `review_context_echo` with `case_id`, `revision`, `current_manifest`, and `actual_output_constraints`. Before RC, coverage updates, or O4, Lead reads the current context and rejects a mismatch as `REJECT-STALE-REVIEW-CONTEXT`; the older affected result is `superseded_context_revision` and is never used to overwrite current artifacts.

Context reconciliation only removes obsolete review-context clarification items. It cannot close a pre-existing Human Gate, pending gate artifact, or `blocked_by_human_gate` state: the ledger, required human receipt, and reporter remain authoritative for those gates, including `HG-02`.

This contract does not yet modify risk-scanner, jurisdiction-auditor, or review-reporter. Consumers must later validate the path, case binding, revision, source constraints, and output constraints before relying on it.
